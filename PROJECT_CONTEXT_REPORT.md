## 1. What this project is

A web application to control weekly branch (sucursal) budgets against actual
spend, administered on the user's own web server.

Core scope (all Phase 1, confirmed with the user):

```text
Pull actual payments per branch from Odoo (one or several branches selectable).
An administrator user enters weekly budgets per branch.
Home page shows two tables:
  1. budget / week / actual spend / remaining (overall)
  2. same breakdown, split by expense type
Expense type is resolved via a provider -> expense-type mapping dictionary.
  The dictionary is provided as an Excel file for now; a future module may
  let admins manage it directly in the app.
Each row of the first table links to a bigger per-branch report:
  payments broken down by provider, several charts, and its own export
  (Excel or an executive PDF report for Direccion General).
User-level permissions (roles) are part of the core app, not an add-on.
```

Explicitly deferred (not Phase 1): branches that are not on Odoo will read
their data from an Excel file stored in SharePoint. Source/format for that
integration has not been discussed yet; will be defined in a later phase.

## 3. Critical technical constraint discovered: MariaDB version

Both the dev and prod MariaDB servers are on old versions:

```text
Dev:  MariaDB 10.4.32
Prod: MariaDB 10.4.28
```

Django's minimum supported MariaDB version has been rising:

```text
Django 6.1 (what `django-admin startproject` generated by default): needs MariaDB 10.11+
Django 5.0+: needs MariaDB 10.5+
Django 4.2 LTS: works with MariaDB 10.4 - CONFIRMED via real migrate + connection test
```

**Decision: pinned to `Django>=4.2,<5.0` in `requirements.txt`**, with a
comment explaining why. Do not casually bump the Django version without
re-checking MariaDB compatibility first, since both dev and prod are capped
at 10.4.x and neither is a versioned bump we control from this side (upgrading
the servers is a separate, real infrastructure decision, deliberately not
taken - see Section 6).

Verified for real (not just exit code 0):
- `manage.py migrate` applied 18 real migrations against the dev DB (auth,
  admin, contenttypes, sessions).
- Queried `SHOW TABLES` directly and got the 10 expected tables back.
- `runserver` returned a real HTTP 200 on `/` and on `/admin/login/`.
- A Django superuser was created and verified in the DB (`is_superuser=True`,
  `is_staff=True`, password check passes).

## 6. Risks / open items flagged to the user (not yet resolved)

```text
1. DJANGO_SECRET_KEY is still blank in core/config/.env as of last check.
   The app falls back to an insecure default key when blank (a real bug
   was found and fixed: os.getenv(key, default) does NOT fall back on an
   empty-but-present value, only on a fully unset one; fixed with `or`).
   User has the real generated key, just hasn't pasted it in yet.

2. MariaDB Strict Mode (mysql.W002) is not enabled on the dev connection.
   Without it, MariaDB silently truncates data that doesn't fit a column
   instead of raising an error. Flagged, not fixed - data integrity risk to
   revisit before production use.

3. Prod DB per-database privileges for the prod DB user (name kept out of this file, see `.env`) on
   `presupuestos_ap` are unverified (see Section 4's "Known gap").

4. Dev server port: Django's default 8000 is taken by XAMPP on this
   machine. Using 8010 instead (documented in README). Port is a runtime
   CLI argument, not stored in any config file - user can pick any other
   free port at any time.

5. Widening the prod DB user (name kept out of this file, see `.env`)'s MySQL grant to allow this dev PC's public
   IP (for remote reconciliation from here) was discussed and intentionally
   NOT done - recommended to leave as `%`... actually already `%` (any
   host), so this is moot; no action needed here. (Kept for history: this
   was raised before the phpMyAdmin screenshot showed the grant is already
   host-open.)
```
